# 云端语音首段“加速/跳读”修复

2026-09-23。稳定版本先独立提交并推送为 `a6b47bc`，本次修复在该提交之后进行，不修改K230固件或ASR/视频设置。

## 根因与复现

- 电脑声卡按8kHz mono PCM16连续写入6秒音频，实际写入耗时6.013秒，停止排空后6.123秒，欠载0；未发现声卡采样时钟加倍。
- 同一条真实云端合成测试回复包含20.32秒音频，仅4.937秒便全部到达。分片是24kHz PCM16原始数据，实测无RIFF头、字节数为偶数；既有24k→8k有状态转换不需改变。
- 旧`broadcast_pcm16_realtime`按网络到达速度把所有20ms帧灌进播放队列；队列只有240帧（4.8秒），满后删除最旧帧。
- 确定性复现：一次送入编号1～500的10秒音频，电脑与设备均只保留最后240帧，第一帧变成261，前5.2秒直接丢失。这能产生开头跳读、听似加速、生成结束后尾段恢复正常的现象，不是要求TTS放慢语速。

## 变更

- 增加`PlaybackClock`，以8kHz PCM真实样本时长调度，最多约160ms预送。使用累计期限而非每帧固定sleep，避免Windows计时器误差逐帧累加。
- 语音队列满时异步等待，不沿用视频的丢旧帧策略。电脑停止消费时显式报错，设备长期阻塞时断开该路，不能静默删除句子。
- 两端使用同一调度和同一PCM；字节计数不翻倍。声音采样率、音色、重采样逻辑保持不变。
- 预录音工作线程通过服务端事件循环分发设备PCM，避免跨事件循环直接修改asyncio队列。
- reset通过世代号终止尚未送出的旧回答，清空音频与节拍；并发启动本机播放线程加锁。
- `/api/device-status`的`audio_stream`增加local_enqueued_bytes、local_written_bytes、device_enqueued_bytes、cancelled_pcm_bytes、device_stalls、local_underruns及dispatch_ahead_sec诊断。

## 验证

| 测试 | 结果 |
|---|---|
| 10秒编号突发回归 | 500帧保序保留，两个输出逐字节匹配，峰值不超过10帧 |
| 满队列 | 生产者等待，开头不被删除 |
| 中断 | 旧回答停止入队，播放时钟复位 |
| 跨事件循环预录音 | 实际分发回到服务端循环 |
| 实际电脑播放20.32秒云端回复 | 总耗时20.344秒，播放器写入跨度20.27秒，欠载0 |
| 数据完整性 | 源PCM、电脑实际写入、设备测试队列均325120字节，逐字节相同 |
| 缓冲 | 两路队列最高8帧，未触及240帧溢出策略 |
| 运行中后端双端测试 | 8000B测试音两路各8000B，电脑写出8000B，设备阻塞0、取消0、欠载0 |
| 全套测试 | 72项通过 |

真实云端回复由独立诊断进程获取并保存到Git忽略目录；实际播放验证使用同一云端PCM，不需要把相机画面或用户录音上传用于此测试。首个诊断请求遇到失效代理，直连仅在诊断客户端启用，没有修改系统代理或持久配置。

此验证确认修复了已复现的音频片段丢失与突发调度；如果用户仍听到音色/语速变化，需另比较完整原始云端语音，不能把模型韵律变化与本地跳段混为一谈。
